# Playwright E2E rules — lab and ephemeral stack

Loaded when Claude Code reads a matching file; Codex and humans read it from the table in [`CLAUDE.md`](../../CLAUDE.md). Breaking one of these is a regression even when the workflow still parses.

**Dispatch**

- Playwright E2E (`novatalks.tests`) is **dispatch only**: the switcher routes `workflow_dispatch` to `ci-e2e-tests-manual.yaml`, passing `tests_ref`, `test_tags`, `env_url` and `botflow_url` from `github.event.inputs`, along with the rest of the form (`report_base_url`, `workers`, `exclude_tags`, `reset_stand`, `target`, `suite_timeout_minutes` and the four image tags), each defaulting as the called workflow does when a caller's form lacks it. Do not bring back a tag route — runs share one stand and create and delete each other's entities, which is why the `concurrency` group keys on `env_url`. That group is not the guarantee: it sees one repository and one spelling of the URL, and GitHub cancels a waiting run when a third arrives. The guarantee is the lease on the stand's own reset service (`novatalks.tests/tools/stand-reset`, `POST /lease`): `Take the stand` waits for it before anything touches the stand, `/drop`, `/prune` and `/normalize` answer `409` to a caller not presenting it in `X-Stand-Lease`, and `Release the stand` runs on `always()`. Keep the lease's minutes above the job's `timeout-minutes`, or a long run loses the stand halfway. **The stand's URLs are inputs, not secrets** (public URLs, and one form must be able to point at another stand), and the four credentials plus the API token are secrets named `E2E_*`, never after a stand. The run needs **seven** environment variables and no more: the suite derives `CLIENT_URL`/`CLIENT_URL_API` from `ENV_URL` and, with `USE_DB` unset, needs no database — so the workflow carries no kubeconfig, no port-forward and no DB credentials, and must not regrow them. Restoring the database, syncing Redis and restarting the engine were removed on 2026-09-17 with the v5 lab: they needed in-cluster access that the deprecated in-cluster runners provided and Hetzner runners do not. Never `FLUSHALL` that stand's Redis — DB 15 holds `nr:flows`, the chatbot logic, which is in no Postgres dump. Pass the tags through step `env:`, never `${{ inputs.* }}` inline in `run:`. A new target (an ephemeral stack from image tags) is a new optional input with a default, so existing callers keep working.

**Ephemeral E2E stack** — `.github/actions/e2e-stack/`, reached by `target: ephemeral` on the E2E workflow. Both targets stay; `lab` is the default and nothing about it changed. Spec: [`docs/superpowers/specs/2026-09-18-e2e-ephemeral-stack.md`](../../docs/superpowers/specs/2026-09-18-e2e-ephemeral-stack.md).

- Every container's environment is **rendered from the published chart** (`helm template` of `novatalks-platform` at a pinned version), never a list kept here — a copy in `nova.ci` rots the moment the product gains a required key. `localise_env` then rewrites what the chart renders for a cluster: in-cluster service names to `127.0.0.1` and `https://localhost` to `http://`. Rewrite **names in host position only** (followed by `:`, `/` or end of value), or `NATS_NAME=e2e-engine-listener` becomes an address. Adding a `-e` per key instead is how four addresses went unnoticed until the lab's render was diffed against this one.
- **Compare against the lab's own values when something behaves differently.** Rendering both and diffing found three faults in one pass that log-reading had missed twice: `AUTH_JWT_TOKEN_EXPIRES_IN` holding a secret placeholder instead of `7d`, four unreachable in-cluster addresses, and the header problem below. The lab's values nest under `novatalks:` (it consumes the chart as a dependency) — flatten that key before rendering.
- **`underscores_in_headers on;` in the front proxy.** The Engine's static credential is `api_access_token`, and nginx drops headers containing underscores. Traefik does not, so the lab never showed it: every API call answered 401 while the token itself was valid. Any check of that token must go **through the proxy** — one sent straight at the container proves the token and nothing about the path the suite uses.
- **`limits.enableAutomaticAgentAssignment` must be `true`, and it is the fourth of the four account settings the two targets share** (with `active_until`, `locale` and `limits.users`; the lab's copy is `novatalks.tests`' `tools/stand-reset/normalize.sql`, and the two must not drift). The engine seeds it `false`, and with it off a conversation handed to a team only ever joins the queue — nothing a single-agent run produces drains it. The first message of a spec still alerts, because the chatbot's transfer forces an assignment; the second sits `open/inqueue` with the agent `online/Idle` beside it. `QANT-45` failed all three attempts, on two separate runs, and passed first try with this one field flipped. It is also why four workers looked *more* stable than one: another worker's traffic is the event that drains the queue, so concurrency was hiding this rather than causing it.
- **The stack runs its own mail server, and the suite uses it whenever `E2E_MAIL_HOST` is set.** GreenMail, pinned by digest, SMTP `3025` and IMAP `3143`, its API moved to `18190` because the runner's nginx holds 8080. IMAP is the point: the engine *polls* for inbound mail, so an SMTP-only catcher cannot stand in. Both engine mailers are overridden to it, host and port only — the chart points the system mailer at `smtp.gmail.com` with no password and the general one at a `maildev` service the stack does not run — and `MAIL_SYSTEM_USER` is set empty so the system mailer sends without AUTH. Neither port offers STARTTLS, so nothing tries TLS against a certificate nobody trusts. Addresses are at `mail.e2e.test`, **not** `.invalid`: the UI's add-agent form caps a top-level domain at six letters. The same step marks the seeded admin as having signed in, because the UI opens its onboarding modal over the page for a user who never has, and on a fresh database that covered the first admin spec's next click.
- **The lab has its own mail server too, and the ukr.net mailbox is QA's, not ours.** That mailbox is what QA uses for its own development testing; every email inbox a lab run created polled it with `EMAIL_DELETE_FETCHED` on. GreenMail runs in the lab's namespace (`novatalks.tests/tools/mail`), both engine mailers point at it through the lab's values, and the suite reaches it through the reset service's `/mail/append`, `/mail/read` and `/mail/clear` routes (the cluster's Traefik serves no IMAP). The workflow's `Point the suite at the lab's mail server` step enables it only after `/mail/read` answers 200, and warns and keeps the external path on a stand without the routes. PrivateBin runs next to the lab as release `privatebin` in namespace `privatebin`, which is the address the chart already gives the engine.
- **The stack runs PrivateBin for referral codes, with its traffic limiter off.** The engine encrypts a paste and uploads it over PrivateBin's v2 API, so a stub cannot stand in; the chart points it at a cluster namespace neither target has, and the referral endpoint answered `500`. The image listens on 8080, which the runner's nginx holds, so it runs on a bridge network published on loopback `18280` — the one container here not on the host network. The limiter refuses a second paste from one address within 10 s and still answers `200` with no paste URL, and every sign-in on this stack comes from `127.0.0.1`.
- **Both targets run production's GeoIP API** (`novatalks.geoip-api`, the image production's `novatalks-system` runs, pinned by digest; its database is inside the image). The engine looks up every sign-in's address with a one-second timeout, and the chart points it at `novatalks-geoip-api.novatalks-system:3000`, a Service neither target had: each sign-in waited out the timeout and logged `GeoIP lookup failed`. The lab gets it at that same address on the dev cluster (`novatalks.tests/tools/geoip`), so its values need no override; the stack runs it on loopback `18300`, because the engine holds 3000, and hands the engine `GEOIP_URL`.
- **The stack seeds one admin per worker, and the suite's default sign-in takes one by worker index.** The engine keeps one session per device type, and 70 spec files sign in as the seeded admin when they name nobody, so parallel workers signed each other out mid-test. `E2E_ADMIN_POOL_SIZE` (7) admins are created through the engine's own API — so each has every row a real agent has — at `mail.e2e.test`, with the seeded admin's password, then given its `type` and a past sign-in. `E2E_ADMIN_POOL` names them; `login.page.ts`'s `defaultAdmin` keeps worker 0 on `UI_ADMIN_LOGIN` and falls back to it past the pool's end or without the variable, The lab gets the same pool from the workflow's `Seed one admin per worker` step (through the API, idempotent on "already in use", before the normalise step), and `novatalks.tests`' `normalize.sql` gives those admins the seeded admin's type — which matters beyond permissions, because the engine leaves `SuperAdmin` users out of agent lists and reports that specs count. The suite's API prune keeps the pool.
- **Every token in `stack.sh` is masked through `mask`, never a bare `printf '::add-mask::'`.** A mask line is an instruction only to the Actions runner. Under `local.sh` it is the value, printed to the terminal: that is how the lab BotFlow's admin session token reached a transcript on 2026-09-23. `mask` prints nothing outside Actions, and `validate.sh` fails on a bare mask anywhere in `.github/actions/e2e-stack/`.
- **The seeded admin password must satisfy the engine's own `DEFAULT_PASSWORD_POLICY`** (8+, upper, lower, digit, special). The suite hands it to every agent it creates, so a non-compliant value seeds fine and is refused at `POST /agents` with `422`, where it reads as a product fault. Same shape as the `@local` admin address above; keep the value obviously fake.
- **Pass `AGENTBOT_INBOX_TOKEN` to the engine before it seeds, and set BotFlow's two tokens to two different values.** The seeds create the AgentBot *and* a random token for it when that variable is unset, which the chart never renders — so the engine signs its calls to BotFlow with a token BotFlow has never seen and BotFlow ignores every one of them in silence. Adding the right token as a second row does not change which one the engine sends; the SQL updates the existing row instead. `NOVATALKS_BOTAGENT_TOKEN` and `NOVATALKS_ENGINE_TOKEN` are separate on the lab, and while both held one placeholder here the connector authenticated against the bot's row by coincidence.
- The origin is `localhost:18080`, **not** 8080: the E2E runner VM already has an nginx bound there, which answered the proxy's health poll for three runs. It is written in `stack.sh` and in the chart values, and the bring-up asserts the two agree.
- **The proxy's certificate is generated before the engine and botflow start, and both mount it as `NODE_EXTRA_CA_CERTS`.** Every channel webhook the chart renders is an `https://localhost:18080` URL, so the engine posts each bot reply to the client *through the proxy*, and Node-RED's own flows call it the same way. Without the CA the engine logs `Could not send webhook message …: self-signed certificate` for every outgoing message and marks it `failed` — which reads downstream as the product losing messages, several steps from a certificate nobody was looking at. The lab has a real certificate and never shows this. Chromium does not read `NODE_EXTRA_CA_CERTS`; it is told to ignore certificate errors in `playwright.config.ts` instead.
- **The dialer needs `ENGINE_URL` and `AGENT_BOT_TOKEN`, and `API_ACCESS_TOKENS` does not cover them.** Its boot environment comes from `targets.sh`'s api-scan arm, which is shaped for a DAST scan and so has neither. `API_ACCESS_TOKENS` only admits the token the engine presents for its own calls; a request from a **logged-in user** arrives carrying that user's engine token, which the dialer has never seen, so its auth middleware asks the engine to vouch for it (`integrationService.fetchTokenInfo`, against `ENGINE_URL`, authenticating with `AGENT_BOT_TOKEN`). With `ENGINE_URL` unset axios throws `Invalid URL`, the middleware's catch-all turns that into a `400`, and the engine proxies the `400` back: the Dialer Settings page renders its header, no rows, and every `@campaigns` spec fails on an input that never appeared. Checking the endpoint with an `api_access_token` answers `200` and proves nothing — that call never takes this branch.
- Flows are copied from the stand at boot and **every address of the stand is rewritten and then checked** — anything left pointing at the lab would have an ephemeral run creating conversations there and writing to its database. There is no fallback document: a stand that cannot be read fails the run.
- `wait_http` treats any answer as up, which is right for a health path and wrong twice over: Node-RED answers on every path (so the botflow wait asserts the code is not 404, which is what the image's own `settings.js` produces), and a port somebody else holds answers too (so the proxy port is checked free first, and the proxy must route `/redbot/` to what botflow serves directly).
- `grep ... | cut` inline under `set -euo pipefail` ends the run with no message when the grep matches nothing. Read rendered keys through `env_value`; keep `|| true` on any grep whose empty result is a legitimate outcome.
