# Trivy, SAST, DAST and dependency-scan rules

Loaded when Claude Code reads a matching file; Codex and humans read it from the table in [`CLAUDE.md`](../../CLAUDE.md). Breaking one of these is a regression even when the workflow still parses.

**Scanning**

- `trivy-scan` must `needs: [build-image]` and scan the exact GHCR tag the build produced.
- Keep auto-scan limited to `main`/`master`/`development` plus the `scan*` trigger, and `warn-only` as the default policy.
- Keep the pinned `aquasecurity/trivy-action`, the ~5-hour DB cache bucket, and the `.report` file with OS and Node.js sections published as artifact and release asset.

**Code scanning (SAST/DAST)**

- `warn-only` governs **findings**. A scanner that could not run reds the job. Never collapse the two.
- A DAST application that fails to boot is a **loud skip** — green build, an explicit `⚠️ not run — <reason>` in the report, the job summary and the notification. Never silence it, never red it: boot failures come from `.env` drift or a missing migration, not from a vulnerability, and a job that is usually red for non-security reasons is a job people stop reading.
- Keep Semgrep and the ZAP image pinned by tag **and** digest, never `latest`. **Do not remove the Semgrep canary rule guard, and do not remove the `.errors[]` check next to it** — the two are halves of one guard. Semgrep reporting zero findings and Semgrep having loaded zero rules are indistinguishable without them, exactly like `gitleaks git --log-opts` exiting 0 on an unresolvable range. The canary alone is not enough: it is mounted from the action's own directory, so it fires even when every registry pack failed to fetch. The canary proves the engine ran, the empty `.errors[]` proves the configs resolved. The guard also asserts a non-empty `.paths.scanned`, and excludes the canary hit from every bucket — `ERROR`, `WARNING` and `INFO` — **by rule ID, not by severity**: severity used to be a caller input, and excluding by check_id instead means the exclusion keeps working regardless of it.
- Semgrep's only directory exclusion is agent tooling: `--exclude=.claude --exclude=.agents` in `scan.sh`, never a per-repository `.semgrepignore`, because a repository's own `.semgrepignore` replaces Semgrep's built-in ignore list. Skills, hooks and scripts there run on a developer's machine and never ship. On `novatalks.ui` they produced two of its three `ERROR`s (NC2-2911). Do not add a directory that ends up in a bundle or an image. Per-finding exceptions stay inline `nosemgrep`.
- Semgrep reports by Semgrep's own severity mapping: `ERROR`/native `CRITICAL`/`HIGH` → high, `WARNING`/`MEDIUM` → medium, `INFO`/`LOW` → low, anything else → high with a warning. `outcome=findings` follows high only. **High and Medium are counted and listed on every run, clean or not**: the old exact-equality filter hid 12 `WARNING` findings on `novatalks.core` from the count *and* the report, and a severity filter that drops Medium from either is that defect again. ZAP reports risk per counted rule through `zap_risk_counts` (`dast-common.sh`): which rules count comes from the console's `WARN-NEW`/`FAIL-NEW` lines, their risk from the `-J` JSON. Never count risk from the report alone, because it lists `IGNORE`d rules too. A missing JSON, a counted rule without a risk, or per-rule lines that disagree with the tally are scanner errors.
- Take the ZAP counts from the single tally line, anchored on `^FAIL-NEW: <digits>` + a **literal tab byte** + `FAIL-INPROG: `, not the bare `^FAIL-NEW: ` prefix — a per-rule FAIL-level line starts with that same prefix and would be matched instead. **Keep the pattern ANSI-C quoted (`$'…\t…'`) so the tab is a real tab byte**, never a plain `'…\t…'` string: BSD grep expands `\t` in a pattern, GNU grep does not (it warns `stray \ before t` and matches a literal `t`). Every runner is GNU, so the plainly quoted form matches nothing in production and every completed scan reports a missing tally and reds the build; only a macOS harness run passes. Never take the counts from the per-rule `WARN-NEW:` lines, and treat a missing or non-numeric tally as a scanner error. The line is printed unconditionally by any completed scan, so its absence means the scan did not finish.
- Keep `0|1|2` in the ZAP exit-code `case`. Exit **1** is `FAIL`-level findings and `-I` does not suppress it — `-I` gates exit 2 alone. Moving 1 back into the error arm reds a trunk build for a finding.
- `.github/actions/dast/zap-baseline.conf` is the triage register. The reason column is a review-time obligation, not a parsed one — `scan.sh` requires three tab-separated fields and accepts an empty third, because ZAP accepts it and the validator must never reject what ZAP accepts. Do not add a check that enforces it. Adding an entry is a risk-acceptance decision, not a CI change. A mistyped rule ID is silently inert; `scan.sh` validates line shape and levels only, and cannot validate IDs. A risk only one repository accepted goes in its overlay, `zap-<mode>.<repository>.conf`, which `scan.sh` appends after the shared file for that repository only, validated the same way. Never use `OUTOFSCOPE` keyed on its port: ZAP drops those alerts before counting, so an accepted risk reports as `PASS` (NC2-2911).
- `dast/action.yml`'s `scan-mode` input (`baseline` default, `full`) reaches `scan.sh` as `DAST_SCAN_MODE` and picks the whole ZAP invocation together — script, spider flag and triage register — never one of the three alone: `zap-baseline.py` / no spider flag / `zap-baseline.conf` under `baseline`, `zap-full-scan.py` / `-j` / `zap-full-scan.conf` under `full`. `-j` swaps ZAP's traditional spider for the modern one — the only way a single-page app is more than one page to ZAP, since nginx serves `index.html` for every route and the traditional spider has no JavaScript to follow. `zap-full-scan.conf` stays its own file, never shared with `zap-baseline.conf`: the active scanner loads the whole active rule set on top of the passive one, and an `IGNORE` carried across would silence a class of finding nobody agreed to accept for that mode. The exit ladder and tally line are identical between the two scripts (verified against `zap-full-scan.py:480` and `:511-522`), so `dast-common.sh` and the `0|1|2` exit case stay shared and unchanged between modes. An unrecognised `scan-mode` is a scanner error, never a silent fallback to `baseline`.
- `dast/action.yml`'s `zap-context` input (empty default) reaches `scan.sh` as `DAST_ZAP_CONTEXT` and, only under `scan-mode: full`, appends `-n <file> -U nova-ci-dast` to the `zap-full-scan.py` invocation — `-n` and `-U` travel together or neither does, same rule as the `-z` replacer below: a context loaded with no user selected scans as nobody while looking configured. A context file (`.github/actions/dast/contexts/<repo>.context`) has to define **both** `loggedInIndicatorRegex` and `loggedOutIndicatorRegex`; one alone lets ZAP silently crawl anonymously while reporting a successful authenticated run. `contexts/novatalks-ui.context` exists — its login request (URL, JSON field names) is verified against `novatalks.ui`'s own source and its published image — but is **not** wired into `targets.sh`: that arm leaves `DT_ZAP_CONTEXT` empty, because `novatalks.ui`'s ephemeral DAST scan boots no backend at all (confirmed live: `POST /auth/sign_in` returns `405`; every route returns the byte-identical static shell regardless of credentials, since the SPA renders auth state client-side where no ZAP-visible HTTP response ever reflects it). Do not fill in a guessed indicator regex to "finish" that arm — a wrong one is worse than none, per this same rule.
- The switcher's inline `sast-scan` is the pull-request feedback path and stays inline for the same reason `secret-scan` does: `novatalks.core`'s PR route is a two-entry `build_target` matrix, and moving the job into the build workflow would scan identical source twice per event. Keep it **advisory** (findings green, only a broken scanner red), keep it on the same thirteen-repository list as `secret-scan`, and keep it notifier-free — a SAST finding is not the pager event a leaked credential is.
- `deps-scan` runs in **two places, for two different readers**. The switcher's inline one is the pull-request path (below). The build workflow's `deps-scan` job is the evidence path: trunk and `scan*` only — the same gate `trivy-scan` uses — because what it adds over the PR run is the `.report` attached to the release, and a release only exists on those builds. `needs: [build-image]` and nothing else, like every other scan job; it does not need the image, only `RELEASE`/`SHORT_REF_NAME`/`SHORT_SHA` to name the report. Same `PUBLISH_RELEASE` rule as `sast-scan` — never publish where it is false, or `action-gh-release` mints a `TRIVY.SCAN_*` git tag per feature build. None of the scan jobs carries an `environment:`: the siblings' `environment: ${{ inputs.environment }}` referenced an input no workflow declared, so it was always empty, and it went on 2026-09-29. Do not add one back without declaring the input and a secret that needs it.
- The dependency notifier line distinguishes **four** outcomes, and `no lockfile found` is the one that matters: a repository nobody could scan and a repository with nothing to find produce the same count, so they must never produce the same line. The clean wording names both tools having parsed something, for the same reason.
- The switcher's inline `deps-scan` reads the checkout's own lockfiles with two independent scanners — `trivy fs --scanners vuln` (called directly in the job, the same place every other Trivy job in this repository calls it — Trivy has no `.github/actions` wrapper rule) and OSV-Scanner (`ghcr.io/google/osv-scanner`, pinned by tag **and** digest like every other scanner image here, invoked only from `.github/actions/deps-scan/scan.sh`; `validate.sh` fails on a direct call). Same thirteen-repository list, same `pull_request` gate, same advisory policy, no notifier, same reason as `sast-scan`: `trivy-scan`'s image scan reads what ships inside a built image and cannot see a manifest-less frontend bundle (`novatalks.ui`'s runtime image has no `node_modules`), a pruned devDependency (`novatalks.core`'s `npm prune --omit=dev`), or a repository that builds no image at all (`novatalks.chatwidget`, `novatalks.ui-lite`, `nova.docs`) or none until after merge. Emits a fourth outcome, `no-manifests`, alongside `clean` / `findings` / `error`: a repository with no lockfile is a legitimate state and must never be reported `clean`, and requires **both** tools to agree there is nothing to scan — one tool's unsupported ecosystem while the other genuinely parsed something is `clean`/`findings` from the tool that parsed, not `no-manifests`. **OSV-Scanner's own exit code, not its JSON body, is what proves it ran**: a real `api.osv.dev` network failure (reproduced with `docker run --network none`) still writes a well-formed JSON document with the lockfile found and the package list populated, and zero vulnerabilities purely because the query never left the container — indistinguishable from a clean scan in the JSON alone. Only exit codes `0` (clean), `1` (`ErrVulnerabilitiesFound`), and `128` (`ErrNoPackagesFound`, empty stdout) are acceptable; every other code (`127` generic, `129` `ErrAPIFailed`, `130` `SIGINT`) is a scanner error even when stdout parses — the same shape as the ZAP `0|1|2` ladder, verified against `cmd/osv-scanner/internal/cmd/run.go` in the pinned `v2.5.1` source rather than assumed. Trivy's own proof is its `.Results[].Packages` count: a `.Results` key entirely absent, or present with zero packages across every entry, is `no-manifest`, never `clean` — verified live, a DB-fetch failure with no cache makes Trivy exit non-zero and write no JSON at all, so a present-but-empty `.Results` is a real, reachable shape, not a guess. The two tools' findings are listed in **separate sections** in the report and summary, never merged into one row or de-duplicated against each other — that cross-check between two independent vulnerability databases is the reason to run both.
- Keep the findings **listed in the job summary**, not only in the `.report` artifact. A summary that states a count and hides the list behind a download is read at the next audit, not by the developer who wrote the code. The cap is 25 with an explicit `Showing 25 of N` note naming the artifact; a silent truncation would be the same defect in a new place.
- Report artifacts never keep the 90-day default, because the quota is the organisation's. **One day** where the `TRIVY.SCAN_*` release holds the report and the summary links there (Trivy, `dast-scan`, `api-scan`). **Fourteen** for Semgrep and `deps-scan`, whose `Showing 25 of N` note names the artifact and whose artifact is the only copy on a pull request or feature build; one day there would turn that note into a dead reference overnight. The `workflow_dispatch` pentest and live-baseline artifacts *are* the report and keep the default. Every report upload in the build, switcher, widget and test workflows is a step-level `continue-on-error`: a full quota is not a scan or test result, and on 2026-09-24 it redded every `sast-scan` and `deps-scan` in the organisation. That is a step, never the job: `unit-test` and `integration-tests` still must not carry it.
- `sast-scan` in the build workflow runs on **every build, on any branch** — Semgrep reads the checkout, so it needs no running app, no database and no seeded stack. Do not re-narrow it to `IS_TRUNK`. The trunk/`scan*` test it used to carry was never about cost; it was about having a release to attach a report to, and it now lives on as the job-level `PUBLISH_RELEASE` env, which gates the `Publish report release` step and chooses the notifier's report URL. **Do not let `sast-scan` publish where `PUBLISH_RELEASE` is false**: the `TRIVY.SCAN_*` release exists only because `trivy-scan` created it, and `action-gh-release` would mint a `TRIVY.SCAN_*` git tag per feature build. The run artifact is the report's copy there, and the notifier links the run instead of a release-download URL that would 404. The widget workflow's `sast-scan` needs no equivalent — `build-widget` creates its release ungated.
- Keep `dast-scan` scoped by the `build-image` `IS_TRUNK` output plus the `scan*` trigger — it boots the built image next to its database, and that cost is the reason. Keep both jobs off `pull_request` entirely: `build-image` does not run there, so there is nothing to scan. `trivy-scan` keeps its own `Resolve scan policy` step on purpose; see spec D6 before "simplifying" two sources of truth into one.
- Keep all three reports on the **one** release the build already creates. The `TRIVY.SCAN_` tag prefix is historical and stays: renaming it breaks the stable URLs in `docs/security/container-scanning.md`, and one release per scanner triples the walk for the quarterly evidence aggregation.
- The ZAP **baseline** (`dast-scan`) is scoped to the three browser-surface repositories — `novatalks.ui`, `novatalks.core`, `nova.botflow`. The baseline is a browser tool: on a headless JSON API it finds a few response headers and nothing a browser would, so the six connectors/services that once ran it (`nova.chatsconnector.{telegram,whatsapp,signal}-client-api`, `novatalks.dialer`, `novatalks.uspacy.connector`, `novatalks.geoip-api`) were removed on 2026-09-01. Their real coverage is the authenticated `api-scan` (below) — wired for four of the six (`telegram`, `whatsapp`, `signal`, `dialer`) as its own per-repo integration each; `novatalks.uspacy.connector` and `novatalks.geoip-api` publish no OpenAPI spec, so they have no `api-scan` path either and are not tracked for one. A repository is added back only with an explicit request **and its port and health path verified against something authoritative** (the deployment chart, the Dockerfile) — never guessed. Resolve them in `.github/actions/dast/targets.sh`'s `dast_resolve_target`, one arm per repository/surface pair; the default arm fails loudly (`::error::` + non-zero exit) rather than guessing.
- Changing any of these `scan.sh` files means adding a scenario to the matching harness in the same change: `scripts/test-sast-scan.sh`, `scripts/test-dast-scan.sh`, or `scripts/test-deps-scan.sh`.
- No workflow may invoke Semgrep or ZAP directly; `validate.sh` fails on it, exactly as it does for Gitleaks.
- Be honest about reach in the docs: the unauthenticated ZAP baseline finds header and cookie hygiene, not logic flaws. Nobody should read the green check as a penetration test. The authenticated `apiscan*` scan adds real logged-in endpoints but stays passive — it finds no IDOR, no privilege escalation and no business-logic flaw, and is not a penetration test either.
- The `apiscan*` job is parameterised: `auth-mode` is `login` (POST username/password, read the token from the response — `novatalks.core`), `db-token` (read the seeded token straight out of the DB with a caller-supplied `SELECT` — the telegram connector), `db-insert` (write a generated token into the DB with a caller-supplied `INSERT`, `%TOKEN%` substituted in, `role_id` filled from a `SELECT ... WHERE role = 'super_admin'` subquery — for whatsapp/signal, whose Dockerfiles `npm prune --omit=dev` away `ts-node` but whose entrypoints still self-seed via compiled JS, so a token exists either way; `db-insert` writes its own rather than depending on the seeder's own key), or `env-token` (generate a token and hand it to the application container as an environment variable — for `novatalks.dialer`, whose auth middleware accepts any token present in `API_ACCESS_TOKENS` — its `accessTokens.findFirst` DB query always runs first and finds nothing, and the env-list match authenticates the token anyway, skipping only the outbound call to the engine; no seed, no stored row, but the query is why this mode still needs a database). Every other mode acquires its token *after* the application container boots; `env-token` is the one mode that cannot — the application reads the variable once, at its own startup — so it generates and `::add-mask::`s the token before the container exists, and the container-start step injects it via `-e <token-env-var>=<token>`. Getting that ordering wrong produces a scan where ZAP and the application hold different tokens: authenticated-looking and completely blind, which is why `scripts/test-dast-api-scan.sh` includes a mutation check for exactly that. The injected header, its scheme prefix and the token `SELECT`/`INSERT` are per-repo inputs; the acquired token is masked with `::add-mask::` whatever its source; an empty token (login returned none, or the `SELECT` matched no row) is a loud skip (`not-run`), never a scan without auth — `db-insert` and `env-token` cannot produce an empty token (both are generated locally, never read back), so their own loud-skip/error paths differ instead: `db-insert`'s is a failed `INSERT` (`not-run` — the migration never created the table, or the role subquery matched no row; its token is `::add-mask::`ed **before** it is interpolated into the statement, and psql's own output is captured and printed on failure rather than discarded, the same evidence rule the setup command follows), `env-token`'s is a missing `token-env-var` name (a **scanner error** — nothing to generate a token for). It runs `zap-api-scan.py` in **safe mode** (`-S`) by default; a `scan-mode` input (`passive` default, `active`) reaches `scan.sh` as `DAST_API_SCAN_MODE` and, only under `active`, drops `-S` — dropping `-S` turns a passive scan into real `POST`/`PUT`/`DELETE` writes against the seeded API, safe only because the stack is the ephemeral one this action starts and kills, so `active` is a deliberate, never-default exception and an unrecognised mode is a scanner error. `scripts/test-dast-api-scan.sh` asserts `-S` on the default, its absence under `active`, and the mask.
- **`DEFAULT_ADMIN_USER` must be a syntactically valid email at a domain that can never be real.** It was `nova-ci-apiscan@local` — `@local` has no top-level domain, the engine's own entrypoint seeder rejects it with Sequelize's `isEmail` validator (`require_tld: true`), the seed throws, the container dies mid-boot, and the job loud-skips with "the image did not come up within 300s", blaming the image for a bad input. Confirmed live on run 33761248644 against `novatalks.core`. It is now `nova-ci-apiscan@example.invalid` — `example.invalid` is RFC 2606 reserved, so it passes `isEmail` and is guaranteed to never resolve to a real mailbox. Either half missing breaks something: a syntactically invalid address fails validation before the scan starts; a syntactically valid but real-domain address risks a live mailbox.
- **`novatalks.core`'s `api` arm carries `AWS_S3_*` boot dummies in `DT_EXTRA_ENV`.** Run 33863826945 loud-skipped with the container log reading `[Nest] ERROR [ExceptionHandler] TypeError: Configuration key "file.awsS3AccessKeyId" does not exist` — `MulterConfigService.createMulterOptions()` runs at module registration, before any request, and `getOrThrow()`s `awsS3AccessKeyId`/`awsS3SecretAccessKey`/`awsS3Endpoint`/`awsS3Region`/`awsS3Bucket` unconditionally, because `FILE_DRIVER` defaults to `s3` and none of the five has a default. The browser-surface baseline never hit this: it seeds the engine from the product repo's own `.env.example`, which defines them; `dast-api/scan.sh` seeds nothing from that file. The scan never uploads a file, so the values only need to exist and parse — use obviously-fake values (`dast-dummy-not-a-real-key`, `http://s3.example.invalid`), never a plausible-looking one: this repository is public, and a plausible fake is indistinguishable from a real leak to anyone — including a secret scanner — reading it later. Do not copy values out of any product repository's own `.env.example`.
- **`novatalks.core`'s `browser` arm carries the same boot dummies as its `api` arm, but only through `DT_UNSEEDED_ENV`, never through `DT_EXTRA_ENV`.** Live pentest run 33882314584 loud-skipped the browser scan with "the image did not come up within 180s — and no .env.example was seeded, because GITHUB_WORKSPACE holds a checkout of 'nova.ci', not of 'novatalks.core'": `dast/scan.sh` (unlike `dast-api/scan.sh`) normally seeds the engine from the product repo's own `.env.example`, which already carries `DEFAULT_ADMIN_USER`/`DEFAULT_USER_PASSWORD` and the real S3 config — `ci-dast-pentest.yaml` runs in `nova.ci`, so that seeding is correctly skipped, and nothing filled the gap. `DT_EXTRA_ENV` was not the fix: `dast/scan.sh` applies it with `-e` *after* `--env-file`, so on the build workflow's own path (where the real `.env.example` is seeded) it would have overridden novatalks.core's real S3 config with dummies — contradicting the `postgres:17.9-trixie`/R2 exception above and changing a scan that already works (`WARN-NEW: 2, PASS: 65`). `DT_UNSEEDED_ENV` is a second, narrower field `dast/scan.sh` only folds into `DAST_EXTRA_ENV` inside the branch where it has already determined nothing was seeded (`scanned_repo != workspace_repo`) — a no-op on every existing caller, live only for `ci-dast-pentest.yaml`. `dast/action.yml`'s `unseeded-env` input carries it; both `ci-build-ntk-on-push-tags-build.yaml`'s "Resolve DAST target" step and `ci-dast-pentest.yaml`'s "Resolve target" step bridge it from `targets.sh`, per the "every `DT_*` must be bridged" rule below, even though it is only ever non-empty in effect on the pentest path. `scripts/test-dast-scan.sh` mutation-tests the guard itself: hoisting the merge out from behind the `scanned_repo != workspace_repo` check makes the "must not apply when seeded" scenario fail.
- **`setup-command` defaults to empty, and that is the right default.** Both images wired up so far migrate and seed from their own `ENTRYPOINT` before serving anything, so the health poll *is* the completion signal and a second run over `docker exec` buys nothing. For `novatalks.core` it is not even possible: its runtime stage installs `nodejs-24` and **not** npm, so `npm run db:setup:prod` can only answer `sh: npm: not found`. Do not restore a non-empty default; configure one per repository only for an image that genuinely does not self-setup.
- **Pass `DATABASE_URL` to the application container, not only the discrete `DATABASE_*` vars.** Prisma reads that and nothing else — the telegram connector's entrypoint died on `P1012 Environment variable not found: DATABASE_URL`. Both conventions are built from the same values handed to the postgres container, exactly as `dast/scan.sh` does, so they cannot name a different database than the one that was started.
- **A boot failure and a setup failure must stay two different messages, and both must print the evidence.** `docker exec` against a container that never started fails on its own, so an image that did not boot used to report `database setup failed`; the `docker inspect -f '{{.State.Running}}'` check ahead of the setup step is what separates them. The setup command's output is **captured and printed on failure**, never `>/dev/null 2>&1` — a loud skip nobody can act on is a dead end. That is also why `ADMIN_PASS` is `::add-mask::`ed at generation, before any container exists to echo it: these failure paths print container logs and nova.ci is public.
- **Keep the `-z` replacer values wrapped in literal single quotes.** `zap-api-scan.py` puts the whole `-z` string through `shlex.split()` before handing it to ZAP (`zap_common.py: add_zap_options`), so an unquoted `replacement=Bearer <token>` arrives as *two* arguments: ZAP sets the header to a bare `Bearer` and drops the token as a stray positional, and the scan runs **unauthenticated while reporting a perfectly plausible result**. `db-token` connectors hid it because their prefix is empty. The harness reproduces ZAP's own `shlex.split` rather than grepping the raw string — grepping passes either way, which is how this survived review.
- The seeded admin password is `openssl rand`-generated per run and stored nowhere — passed via `DEFAULT_ADMIN_USER` / `DEFAULT_USER_PASSWORD`, used once to log in. Serving the spec can be conditional: the engine needs `SWAGGER_ENABLE=true` (its `swagger-enable` input) or `/api-docs-json` is empty and the scan is a loud skip; the telegram connector serves it unconditionally and sets the input `false`. Keep it opt-in — `apiscan*` tag on `novatalks.core` (`login`), `nova.chatsconnector.telegram-client-api` (`db-token`), `…whatsapp-client-api`/`…signal-client-api` (`db-insert`) or `novatalks.dialer` (`env-token`) only. The `::add-mask::` matters because `tee` copies ZAP's replacer echo (token included) to the persisted, world-readable step log, which deleting the console file cannot undo.
- Each connector's auth model is verified against its own code before its `targets.sh` arm is written. Telegram's `db-token`/`api_access_token`/`tokens` shape is **not** assumed for the Sequelize connectors (`whatsapp`, `signal`) or `novatalks.dialer`, each with its own token storage, header and seed path verified independently — including `signal`, expected to match `whatsapp` and checked anyway: same schema and header, but no health controller at all (`/`, not `/health`) and a `Joi` env-validation schema `whatsapp` has no equivalent of (`STORAGE_PATH`/`S3_*` boot dummies). `novatalks.dialer`'s auth-mode is `env-token`, not `db-token`/`db-insert`: its `auth.middleware.ts` accepts any token in `app.apiAccessTokens`, built by splitting `API_ACCESS_TOKENS` — there is no database row behind it. All four connectors now have a `targets.sh` arm; `novatalks.uspacy.connector` and `novatalks.geoip-api` do not and are not tracked for one — neither publishes an OpenAPI spec, which `api-scan` requires and has no spider fallback for.
- `novatalks.dialer`'s `api` arm also carries `DT_NEEDS_NATS=true`: its `nats.config.ts` `registerAs` factory calls `NATS_SUBJECTS.split(',')` unconditionally at config-load time and `main.ts` awaits a real NATS connection before `app.listen()`, regardless of the auth surface being scanned. `dast-api/action.yml`'s `needs-nats` input (default `false`, matching `dast/action.yml`'s shape) reaches `scan.sh` as `DAST_NEEDS_NATS`. The bring-up itself — `nats:2.10-alpine -js -m 8222`, the `http://127.0.0.1:8222/healthz` poll, and creating the `campaign` JetStream stream — is `dast_bring_up_nats` in `dast-common.sh`, shared by `dast/scan.sh` and `dast-api/scan.sh` rather than kept as two copies: the only repository that needs it is scanned by both actions, and a second inline copy is exactly the divergent-copy hazard `dast-common.sh` exists to remove. It mirrors `~/novatalks/scripts/nats-docker/scripts/js-init.sh`, the stand the team already uses locally — same stream, same subjects, same retention — minus its `nsc push` step, which provisions JWT accounts this unauthenticated server has no use for; if that script's stream changes, this should follow.
- `novatalks.geoip-api` gets **no DAST at all** — no baseline (never a browser surface), no `api-scan`, no pentest — by explicit decision, not by oversight. It keeps Trivy, Semgrep and secret detection. Reason: no authentication (grepped the whole ~220-line single-file Fastify service — no guard, no middleware, no header check) and no OpenAPI spec (no `@fastify/swagger` dependency), and `api-scan` is spec-driven with no spider fallback. It has no `targets.sh` arm for either surface and is not offered in `ci-dast-pentest.yaml`'s `repository` dropdown either — a choice that always fails loudly at `Resolve target` is worse than not offering it. Revisiting this needs an explicit request, never a rediscovery of the same absence.
- The tally-line anchor, `tally_at` and the numeric guard live in `.github/actions/dast/dast-common.sh` and are sourced by all four ZAP callers (`dast`, `dast-api`, the live baseline, and the pentest workflow's live-target step). Never re-inline or copy them — the ANSI-C `\t` and the shape-not-prefix anchor are exactly the divergent-copy hazard the shared file exists to remove.
- **Neither `scan.sh` may infer the repository it is scanning from the repository it is running in.** Both take a `target-repository` input (`DAST_TARGET_REPO`), defaulting to empty and falling back to `${GITHUB_REPOSITORY##*/}` — byte-identical for the reusable build workflow, which runs in the product repository's own context. `ci-dast-pentest.yaml` does not: it runs in `nova.ci`. Two things key off that name and both were silently wrong there. The postgres major version took the `*)` arm, so `novatalks.core` got `postgres:16` and nothing said so — the choice is now **logged with the repository it was made for and where that name came from**. And `dast/scan.sh` seeded `${GITHUB_WORKSPACE}/.env.example`, which under that workflow is `nova.ci`'s own (four MCP variables): the engine would have booted with somebody else's configuration, logged a plausible `seeded 4 variable(s)`, died, and reported `⚠️ not run — the image did not come up` — blaming the image for our input, the same shape as the `@local` admin address. Seeding is now gated on the workspace actually being the target repository's checkout; when it is not, nothing is seeded, a `::warning::` says which checkout was found, and the boot-failure loud skip carries that reason with it. A **warning, not a loud skip**, deliberately: `novatalks.ui` is a static nginx image that needs no seeding, and a scan that can still run must not be stopped by a file it never wanted.
- The per-repository DAST table (port, health path, auth) lives in exactly one place, `.github/actions/dast/targets.sh`'s `dast_resolve_target <repo> <api|browser>`, reached by every consumer exclusively through `.github/actions/dast-target`, a composite action that sources it relative to its own `github.action_path` and emits every `DT_*` value as a step output — `ci-build-ntk-on-push-tags-build.yaml`'s `Resolve DAST target` and `Resolve api-scan target` steps and `ci-dast-pentest.yaml`'s `Resolve target` step all call it (`uses:`, not `run:`). **Do not source `targets.sh` from a workflow's own `run:` step via `${GITHUB_WORKSPACE}` or a relative path.** `ci-build-ntk-on-push-tags-build.yaml` is a `workflow_call` reusable workflow: its `GITHUB_WORKSPACE` is whichever product repository called it (`nova.botflow`, `novatalks.core`, ...), not `nova.ci`, and `targets.sh` has never lived there — a direct `. "${GITHUB_WORKSPACE}/.github/actions/dast/targets.sh"` step broke `dast-scan` and `api-scan` outright for every repository (`nova.botflow` run 33955935398) until `dast-target` replaced it. `uses:` has no such problem: GitHub checks out the whole calling repository next to the action, so `github.action_path` always points at `nova.ci`, at the ref the action is pinned to, regardless of whose checkout `GITHUB_WORKSPACE` holds — the same mechanism `gitleaks/action.yml`'s own comment documents for its central config. `scripts/validate.sh`'s "GITHUB_WORKSPACE self-reference" guard fails any `workflow_call`-triggered workflow that sources a nova.ci path via `GITHUB_WORKSPACE`, so this class of regression reds the harness instead of shipping quietly. Never re-inline or copy an arm into a workflow's own `case` statement — that is exactly the divergent-copy hazard the shared file exists to remove. Every arm sets every `DT_*` variable (even ones with no consumer yet), so an unset field can never leak from the previous caller. **Every `DT_*` the table sets must also be bridged to its consumer** — `DT_ZAP_CONTEXT` was set by the table, declared on `dast/action.yml` and honoured by `dast/scan.sh`, and no resolve step emitted it, so setting it on an arm and watching the harness pass would still have produced an anonymous crawl. `scripts/test-dast-targets.sh` now asserts both directions against `dast-target/action.yml`'s resolve step (the one that promises to emit every key) and, for whether each key is actually read, against `ci-dast-pentest.yaml` (the one consumer that reads every key, since it serves both surfaces): nothing the table sets goes unemitted, and nothing emitted goes unread. Changing `targets.sh` means updating `scripts/test-dast-targets.sh` in the same change.
- The live-baseline workflow (`ci-dast-live-baseline.yaml`) validates its `target` input against a one-host allowlist before scanning; adding a host is a deliberate edit to that `case`, never a runtime choice. It documents the SPA-200 caveat in its own report — duplicate header findings are not extra coverage. It notifies through `notify/action.yml` from this repository's own secrets and degrades to artifact-only when they are unset (a `workflow_dispatch` run does not inherit a caller's secrets). The notification carries the artifact's own download URL as well as the run URL — there is no release to link, so the artifact *is* the report. That is why the scan step emits a verdict line only and a separate `Compose notification` step adds the links: `artifact-url` is an output of the upload step and cannot exist earlier. No artifact, no `📥` line.
- `ci-dast-pentest.yaml` is the one workflow in this repository that runs the scanners in **active** mode (`dast-api`'s `scan-mode: active`, `dast`'s `scan-mode: full`) — real injection, traversal, command-execution and `POST`/`PUT`/`DELETE` payloads, never `warn-only`ed away. Keep it `workflow_dispatch` only, **no `schedule:`** — an attacking scan is a decision someone makes, with an actor and a timestamp against the run. Keep `repository` a `type: choice` with **no free-text URL input anywhere in this file**: the target (port, health path, auth) is derived from the same `dast_resolve_target` table every other DAST caller uses, never typed in. `novatalks.ui` and `novatalks.geoip-api` are deliberately absent from this dropdown, not just unwired: `novatalks.ui`'s ephemeral image is a static SPA with no backend — every route returns the byte-identical shell — so an active scan of it finds nothing a scan of one page would not (its passive baseline still covers it; only the pentest excludes it, and its `targets.sh` browser arm is untouched); `novatalks.geoip-api` gets no DAST at all, see above. Only seven of the twelve remaining repository/surface pairs in this dropdown have a `targets.sh` arm today; choosing an unwired one (e.g. `nova.botflow` on `api`, or any connector's `browser` surface) fails loudly at the resolve step, for the `target: ephemeral` path — that is correct, not a bug, and is not a reason to add placeholder arms. Its `Resolve target` step (gated on `target: ephemeral`) emits **every** `DT_*` key unconditionally (not just the surface-specific ones), because the step serves both the `dast-api` and `dast` scan steps and the browser step needs `needs-db`/`needs-nats` regardless of which surface was chosen — copying only the api-scan output block would boot a browser pentest with no database. Its `target` input defaults to `ephemeral` — a GHCR image this workflow itself boots and tears down, never the live deployment. Same report/notification split as the live baseline: run-artifact only (`if-no-files-found: warn`, no release to attach to), verdict composed in the scan step, links assembled afterwards in `Compose notification` once `artifact-url` exists. **`image_tag` is required for `target: ephemeral` only** (`required: false` at the input level, enforced by a guard in `Resolve target`, which does not run for `target: live`), with no "leave blank for the most recent" lookup and no GHCR login step — both were tried and removed: `nova.ci`'s own `GITHUB_TOKEN` cannot read a package published by a different repository, and the registry's tag list is not date-ordered, so a "most recent" heuristic would risk silently scanning a stale image and reporting the pentest as current. Every package in the org is public, so `docker pull` needs no login and the job carries no `packages:` permission.
- `target: live` is **browser-surface only**: `Validate live target` rejects `surface: api` before anything is scanned, because the live path runs `zap-full-scan.py` straight at the host — no image to boot means no seeded database to read a token out of and no spec to drive `zap-api-scan.py` from, so `surface: api` was an anonymous browser crawl reported as an API scan in the banner, the job summary and the notification. A mislabelled artifact is worse than a missing one; `scripts/validate.sh` asserts the rejection is still present, and the live step's `-j` is unconditional because of it. `target: live` points the same active pentest scan at a real, running host instead of an ephemeral container — **real writes and deletions**, entities created, settings changed, data possibly broken. It is acceptable at all only because the allowlisted host is a dedicated security-testing instance, never production. Keep the allowlist as the whole safety mechanism: one host, named in a `case` inside `ci-dast-pentest.yaml` (`Validate live target` step, `id: confirm_live`) and nowhere else — adding a host is a deliberate edit to that `case`, never a runtime choice, same shape as the live-baseline allowlist. **Compare `confirm` to the host name literally**, and fail before anything is scanned on a mismatch — typing the host name is the point: it cannot be done by accident and it cannot be done without reading which host is about to be attacked. Do not weaken this to a checkbox or a boolean input. The `id: confirm_live` matters structurally, not just cosmetically: the live scan step reads `steps.confirm_live.outputs.host`, and a reference to a missing step output silently evaluates to the empty string in GitHub Actions rather than erroring — a missing or renamed `id` here produces `https://` as the scan target, a broken scan that reports something plausible. The two ephemeral scan steps (`Active API scan`, `Active browser scan`) are gated on `inputs.target == 'ephemeral'` so exactly one path — ephemeral or live — can ever run per dispatch. The inline `Active scan against the live host` step is the one place in this workflow (besides `ci-dast-live-baseline.yaml`) that invokes `zap-full-scan.py` directly, because neither `dast` nor `dast-api` applies to a host with no image to boot and no token to seed; `scripts/validate.sh`'s ZAP-direct-invocation guard exempts this file from the blanket "no workflow runs ZAP directly" check (next to the pre-existing whole-file exemption for `ci-dast-live-baseline.yaml`, which has no ephemeral path to protect) and instead asserts, by a separate line count, that this file contains **exactly one** direct ZAP invocation line — the live path's. A file-path exclusion cannot say "except these lines"; the count is what keeps the ephemeral path honestly covered despite the exemption. Do not widen either exemption beyond these two files, and do not replace the count assertion with a second blanket exclusion. It keeps the same `0|1|2` exit ladder as every other ZAP caller and sources `zap_tally_parse` from `dast-common.sh`, never re-inlining the tally anchor. **The result must be unmistakable three months later**: the report's first line, the job summary banner and the notification message each carry `⚠️ LIVE TARGET <host> — this scan performed real writes. Dispatched by <actor>.` — a report that could pass for an ephemeral run is exactly the failure this requirement exists to prevent.
